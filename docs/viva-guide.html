Project summary

Start with this if the examiner says "tell us about your project". It takes about 45 seconds to say.

SignSpeak converts Indian Sign Language fingerspelling into text and speech in real time, using only a laptop webcam. For every video frame, MediaPipe finds the hands. We crop both hands the same way the training images were cropped, and a MobileNetV2 network, fine-tuned from ImageNet through transfer learning, classifies the crop as one of the 26 letters.

Single-frame predictions flicker, so we average them over 7 frames, and a letter is typed only after it has been held confidently for one second. Lowering your hands finishes the word, and the word is spoken aloud. The model scores 90.6% on the RealSign test set.

The dataset has only four signers, so we added personalisation: users record their own signs, and the app retrains only the last layer, in about a minute on a CPU. For our user, that raised accuracy from 57.6% to 98.6%. Everything runs offline, in a local web app.

The problem

Most hearing people don't know sign language, and interpreters are scarce, so deaf and hard-of-hearing people often can't communicate directly with them. Fingerspelling (spelling a word letter by letter) is how signers give names, places and any word that has no sign.

Most existing tools and datasets are for American Sign Language. In the ISL alphabet, most letters use both hands, while ASL letters use one. A one-hand ASL system therefore can't simply be reused for ISL.

What SignSpeak does

  • Translate: sign letters → text → speech, with on-screen confidence, a hold-to-type progress bar and the letter's reference photo.
  • Learn: practise the alphabet. The app shows a target letter and tracks per-letter statistics.
  • Personalise: record your own signs and fine-tune the model from the browser, with before/after accuracy.
  • Runs offline on a normal laptop CPU. Camera frames never leave the computer.

How it works: the recognition pipeline

Each camera frame goes through these ten steps. The same engine (signspeak/engine.py) powers both the web app and the OpenCV window version (webcam.py).

  1. Browser

    Capture

    The browser opens the webcam (640×480). It draws the unmirrored frame to a canvas, scales it to at most 640 px wide, JPEG-encodes it (quality 0.75) and sends it over a WebSocket.

  2. Vision

    Decode

    The server decodes the JPEG into an OpenCV BGR image. Frames over 3 MB are rejected.

  3. Vision

    Detect hands

    MediaPipe Hands returns up to 2 hands, with 21 (x, y) landmarks each. Each hand's landmarks give a bounding box.

  4. Vision

    Select the sign

    Take the largest hand, plus any other hand within one hand-length of it. Join their boxes into one.

  5. Vision

    Frame the crop

    Add margins of 33% left/right and 29% top/bottom, calibrated on the dataset, and clip to the frame. Cut the crop before anything is drawn on the frame.

  6. Vision

    Prepare input

    Convert BGR → RGB and stretch to 224×224, as the training images were. Pixel values stay 0–255; the model scales them itself.

  7. Model

    Classify

    MobileNetV2 → global average pooling → dropout → Dense(26, softmax). The crop and its mirror image are classified together, and the two results are averaged.

  8. Decision

    Smooth & gate

    Average the probabilities over the last 7 frames. A letter counts only if its smoothed probability is ≥ 0.60; otherwise it is "uncertain".

  9. Decision

    Compose text

    A letter is typed after being held for 1 s (and at least 3 frames). It must be released for 0.3 s before it can repeat. With no hands for 2 s, a space is typed.

  10. Output

    Display & speak

    A JSON result returns to the browser, which draws the landmarks and box over the video and updates the text. A finished word is spoken.

Key concepts

Each concept is explained in general terms first, followed by exactly how SignSpeak uses it. The "In SignSpeak" boxes are what make your answers specific to your project.

A. The deep learning model

Convolutional neural network (CNN)

A neural network that slides small learned filters over an image. Early layers respond to edges and textures, and deeper layers combine those into shapes and parts (fingers, palms). Strides or pooling shrink the image's width and height as the number of feature channels grows.

In SignSpeakA 224×224×3 hand crop becomes a 7×7×1280 feature map, which becomes 26 letter probabilities.

Transfer learning

Start from a network already trained on a huge dataset, here ImageNet (about 1.28 million images in 1,000 classes), and reuse its learned features for a new task. Only a small task-specific "head" is trained from scratch, so far less data and compute are needed.

In SignSpeakMobileNetV2 with ImageNet weights. Its 1,000-class top is removed and replaced with a 26-letter head. About 26k images from 4 signers is far too little to train a deep CNN from scratch without overfitting.

Where: train.py → build_model()

MobileNetV2

A CNN designed for phones and CPUs (Sandler et al., 2018). It rests on two ideas:

  • Depthwise separable convolution: a standard convolution is split into a 3×3 filter applied to each channel separately (depthwise), followed by a 1×1 convolution that mixes the channels (pointwise). For 3×3 kernels, this needs about 8–9× fewer multiply-adds.
  • Inverted residual block with linear bottleneck: a 1×1 conv first expands the narrow input (×6), a 3×3 depthwise conv filters it, and a 1×1 conv projects it back to narrow without ReLU. A skip connection joins the narrow ends. The last step is linear because ReLU in a low-dimensional space destroys information.
cost(separable) / cost(standard) = (k²·M + M·N) / (k²·M·N) = 1/N + 1/k² k = kernel size, M / N = input / output channels
In SignSpeakThe backbone is mobilenetv2_1.00_224 (width multiplier 1.0, 224 px input), with 154 layers and 2,257,984 parameters. The whole model has 2,291,290 parameters (22 MB), small enough for real time on a laptop CPU. For comparison, ResNet-50 has about 25.6 M parameters and VGG-16 about 138 M.

The classification head: global average pooling → dropout → dense softmax

  • Global average pooling (GAP) averages each of the 1280 feature maps (7×7) into a single number, giving a 1280-number feature vector, also called an embedding.
  • Dropout (0.2) randomly zeroes 20% of those numbers, during training only, so the network can't rely on any one feature.
  • Dense(26) with softmax turns them into one probability per letter, summing to 1.
pi = ezi / Σj ezj   ·   head parameters = 1280 × 26 + 26 = 33,306

Why GAP and not Flatten? Flatten would give 7×7×1280 = 62,720 inputs, so the dense layer would need about 1.63 M weights instead of 33k. Fewer parameters mean less overfitting, and averaging also makes the head less sensitive to exactly where the hand appears.

Loss function and optimiser

Categorical cross-entropy is the standard loss for choosing one class out of many. It is small when the model gives the true letter a high probability, and very large when the model is confidently wrong. Adam is gradient descent with momentum and a separate, adaptive learning rate for each parameter.

L = − log py y = the true letter
In SignSpeakBatch size 32. Early stopping watches validation accuracy (patience 3 epochs) and restores the best weights. Images are loaded by a tf.data pipeline (shuffle → parallel decode/resize → batch → prefetch).

Preprocessing

OpenCV stores images as BGR, while the model expects RGB. The crop is resized (stretched) to 224×224 with bilinear interpolation. MobileNetV2 expects pixels in [−1, 1]:

x′ = x / 127.5 − 1 0 → −1, 255 → +1
In SignSpeakThe scaling happens inside the model: a Lambda layer calling preprocess_input in the original model, and an identical Rescaling layer in train.py. The app passes raw 0–255 values, so the scaling can never be applied twice. Because of the Lambda layer, loading the original model needs custom_objects={"preprocess_input": …}.

Where: signspeak/model.py → to_model_input(), load_keras_model()

Data augmentation

Random changes are applied to training images so the model sees more variety than the dataset contains, which reduces overfitting. Keras augmentation layers are active during training only; at inference they do nothing.

In SignSpeakRotation ±18° (factor 0.05 of a full turn), zoom ±10%, translation ±10%, contrast ±10%, with reflect padding. These imitate the small shifts and lighting changes of a live webcam.

Two-stage training and frozen BatchNorm

  1. Stage 1, head only: the backbone is frozen and only the new head trains (Adam, learning rate 1e-3, up to 5 epochs).
  2. Stage 2, fine-tuning: the top of the backbone, from block_14_expand onward, is unfrozen and trained at a learning rate 100× smaller (1e-5, up to 10 epochs).

Why two stages? A freshly initialised head produces large, noisy gradients. If the backbone were trainable at that point, those gradients would damage the pretrained features.

Why freeze BatchNorm? BatchNorm layers store running means and variances learned from ImageNet. Updating them from small batches of new data would shift those statistics and destabilise the network. The backbone is therefore called with training=False, and BatchNorm layers are never unfrozen.

In SignSpeakIn the shipped model, 20 backbone layers (about 1.51 M parameters) were trainable in stage 2. On a laptop CPU, one full epoch takes about 45 minutes; a GPU (e.g. Google Colab) is much faster.

Overfitting and how we prevented it

Overfitting means memorising the training images instead of learning the general pattern. The sign is high training accuracy with low validation/test accuracy.

In SignSpeakTransfer learning, data augmentation, dropout 0.2, early stopping, and separate Validation (100 per letter) and Testing (200 per letter) splits. The test split is used only for the final numbers.

B. Computer vision

MediaPipe Hands

Google's on-device hand-tracking pipeline. A palm detector finds where the hands are, and a hand-landmark model then predicts 21 3-D keypoints per hand: the wrist plus 4 points along each finger. On video it tracks the hand from the previous frame and runs the detector again only when tracking is lost, which keeps it fast.

In SignSpeakUp to 2 hands, with detection and tracking confidence 0.5. The landmarks give each hand's bounding box (clamped to the frame) and are sent to the browser to draw the hand skeleton. evaluate.py uses static_image_mode=True because it works on separate photos.

Where: signspeak/hands.py → HandTracker

Sign crop geometry: handling two-handed letters

  • Keep the largest hand, plus any hand whose box is within 1× the larger hand's longer side. Two-handed letters touch or overlap, while a stranger's hand elsewhere in the frame is ignored.
  • Join the boxes into one, then add margins: 33% of the width left and right, and 29% of the height top and bottom.
  • The margins were calibrated on the Validation split by comparing MediaPipe's hand box with each dataset image (median margins: left 0.42, top 0.27, right 0.24, bottom 0.31). They were then made symmetric, so left- and right-handed signers are treated alike.
  • The crop is cut before anything is drawn on the frame, so the model never sees the drawn skeleton.

Where: signspeak/hands.py → select_sign_boxes(), context_box(), sign_crop()

Train–serve consistency: stretch, don't pad

A model only works reliably on inputs that look like its training data. When the two differ, the mismatch is called training–serving skew, a form of domain shift. The RealSign images are tight, non-square crops that were stretched to 224×224, so the network learned slightly stretched hands.

In SignSpeakThe app reproduces exactly that framing and stretching. In the simulated-webcam test, every margin setting from 0.25 to 0.40 scored 84.5–85.5%, against 80.6% for a square crop that keeps the aspect ratio. What matters is the dataset-like framing, not the exact margins.

Test-time augmentation: flip averaging

At prediction time, the crop and its mirror image are classified, and the two probability vectors are averaged.

p = ½ [ f(x) + f(mirror(x)) ]

Why: the dataset mixes mirrored and unmirrored photos, users may be left- or right-handed, and some cameras mirror the image. Averaging makes all of these equally reliable.

In SignSpeakTest accuracy: 90.7% for the images as stored, 91.1% for their mirror images, and 91.3% averaged. Both images go through the model in a single batch, so it costs only about 1.3× the compute.

C. Real-time decision logic

Temporal smoothing (moving average)

Predictions jump around while the hands move between signs. SignSpeak averages the probability vectors of the last 7 frames, stored in a fixed-length queue (a deque), and clears the history when the hands disappear.

p̄t = (1/7) · Σk=0…6 pt−k

Where: signspeak/model.py → PredictionSmoother

Confidence threshold

A letter counts only if its smoothed probability is ≥ 0.60; otherwise the UI shows "uncertain". This is a precision/speed trade-off. A higher threshold means fewer wrong letters, but signs must be clearer and typing is slower. Users can change it in Settings, between 0 and 1.

The text composer: a small state machine

The composer turns the noisy stream of per-frame letters into clean text. It works on the same idea as debouncing a physical button: a signal must be stable for a while before it counts.

Armedready to type
confident letter appears
Holding "L"timer runs; any change resets it
held ≥ 1 s and ≥ 3 frames → type L
Waiting for release"L" won't repeat yet
↩ released for ≥ 0.3 s (no hand, uncertain, or a different letter) → back to Armed. Signing L again now types a second L.
  • Hold to confirm: 1 s and at least 3 frames, so a stalled frame rate can't type from one or two frames.
  • Double letters (the LL in HELLO): relax your hands briefly, then sign the letter again.
  • Auto space: no hands for 2 s after a letter → a space is typed, once per word. This finishes the word, and the word is spoken.
  • Editing: space, backspace and clear, from buttons or keys. Text is capped at 500 characters.

Where: signspeak/composer.py → TextComposer.update(). 22 unit tests cover these rules.

Learn mode (practice)

The app shows a target letter with its reference photo. Holding the correct sign for 0.8 s counts as correct. Order can be random (never the same letter twice in a row) or sequential. The app tracks attempts, correct answers and the best time per letter, plus a streak. The logic needs no camera or model, so it is fully unit-tested.

Where: signspeak/practice.py → PracticeSession

D. Personalisation (fine-tuning to one user)

Why personalise: domain shift

The model learned from only 4 signers. A new person brings different hands, skin tone, camera, lighting, background, and their own way of forming each letter. When test conditions differ from training conditions like this, it is called domain shift.

In SignSpeakOn our user's held-out recordings, the original model scored only 57.6%. A, D, F, N, R and T were all at 0%, and D was read as P 29 times.

Recording data in takes

For each letter, the user records 3 takes of 20 images (one saved every 0.12 s), moving their hands slightly so the examples vary. Each saved image is exactly the crop the classifier sees. Recordings are stored only on the computer, in data/user/<LETTER>/takeNN_NNN.jpg.

Where: collect.py or the Personalise tab; signspeak/userdata.py → TakeRecorder

Feature extraction: train only the last layer

The backbone stays frozen, so each image's 1280-number feature vector (and its mirror's) only needs to be computed once. Training then works on these short vectors, not images. It amounts to fitting a softmax (logistic-regression) layer: 40 epochs, Adam 1e-3, batch 64, dropout 0.2. It takes about a minute on a laptop CPU.

Masked weight update

Only the weights of letters the user actually recorded are allowed to change. Every other letter keeps exactly its original weights.

W = W0 + ΔW ⊙ m,   b = b0 + Δb ⊙ m,   mj = 1 if letter j was recorded, else 0
In SignSpeakWhen the whole layer was retrained, the letter I dropped from 100% to 73% on the dataset, even though I was never recorded. With the mask, an unrecorded letter can't be pulled towards another one.

Where: finetune.py → masked_dense()

Replay against catastrophic forgetting

Catastrophic forgetting: a network fine-tuned only on new data quickly forgets what it knew. Replay mixes a sample of the original training data into the new training set.

In SignSpeak100 original images per letter (2,600 in total, plus their mirror images) are mixed with the user's recordings. Each letter's recordings are weighted to count as much as that letter's replay images. Another 780 dataset test images (30 per letter) check for regressions; accuracy on them went from 91.5% to 91.7%, so nothing got worse.

Splitting by take, to avoid data leakage

Frames within one take are almost identical. A random split by frame would put near-copies of the same image into both training and validation. That is data leakage, and it inflates the score. Instead, the last take of each letter is held out for validation.

Where: signspeak/userdata.py → split_by_take()

Shortcut learning: why every letter must be recorded

We first recorded only the six letters that were misread (D, P, N, M, T, K). They rose from 34% to 96%, but F, H and R then stopped working for that user, even though their weights hadn't changed. Every training image from the user's camera and room belonged to one of those six letters. The model had partly learned "this camera means one of these six", a spurious correlation, or shortcut. The dataset check couldn't catch it, because it uses the dataset's photos, not the user's camera.

In SignSpeakFix: record all 26 letters. The camera then no longer predicts the label, so the model has to rely on hand shape. Result: 57.6% → 98.6% on held-out takes. Every letter scored 100% except H (80%) and M (87%). finetune.py now warns when letters are missing.

Shipping features instead of the dataset

Fine-tuning needs only the features of the replay and test images, not the images themselves. These ship as models/replay_features.npz: float16, about 15 MB, instead of the 657 MB dataset. A fresh copy of the project can therefore personalise without downloading anything.

In SignSpeakSafety check: a SHA-256 fingerprint of every weight before the final layer is stored in the bundle, and fine-tuning refuses a bundle that doesn't match the model. Personalised models share the same feature extractor, so they still match. After saving, the model is reloaded and its predictions are compared with the trained head (max difference ≤ 1e-4).

E. Evaluation

Dataset and splits

RealSign Indian Sign Language Dataset (CC0, public domain): about 26,000 photos of ISL letters A–Z from 4 signers, already split into Training (700 per letter), Validation (100) and Testing (200).

  • Validation guides decisions such as early stopping and calibrating the crop margins.
  • Testing is used only for the final figures, so they are an unbiased estimate.
  • Two files named .jpg are actually Python scripts. They are detected by their magic bytes (JPEG starts with FF D8 FF, PNG with 89 50 4E 47, BMP with BM) and skipped, leaving 5,198 test images.

Metrics

  • Accuracy = correct / total. This is a fair metric here because the classes are balanced (200 test images per letter).
  • Per-letter accuracy (this equals each letter's recall) shows which letters are weak.
  • The confusion matrix has one row per true letter and one column per predicted letter. It shows which letters get mixed up (exported with evaluate.py --confusion-csv).
precision = TP / (TP + FP)  ·  recall = TP / (TP + FN)  ·  F1 = 2PR / (P + R)

Two evaluation settings

  1. Images as stored: exactly how the model was trained → 90.6%.
  2. Simulated webcam (--crop hands): each test image is placed in a larger frame by repeating its edges, MediaPipe detects the hands, and the app's own crop is applied → 84.8%. This tests the whole vision pipeline and is a better guide to live accuracy.

Where: evaluate.py

F. Web app and systems

FastAPI, Uvicorn and ASGI

FastAPI is a Python web framework, and Uvicorn is the server that runs it. They communicate through ASGI, the asynchronous Python web-server interface, which supports long-lived WebSocket connections and async handlers.

In SignSpeakHTTP routes: GET /api/state, POST /api/finetune, GET /api/finetune, POST /api/recordings/{letter}/delete-last. One WebSocket: /ws.

WebSocket protocol

A WebSocket is a single persistent, two-way connection. Unlike separate HTTP requests, there is no handshake or header overhead per message, and the server can push data at any time.

In SignSpeakThe browser sends binary JPEG frames and the server answers each with one JSON result: hands, box, best letter, confidence, top 3, typed character, text and hold progress. Control messages are JSON with a type (hello, config, model, mode, command, learn_start, record_start, …). The client reconnects automatically with increasing delays (1 → 10 s).

Backpressure: one frame in flight

The browser sends the next frame only after the result for the previous one arrives. Frames therefore never pile up in a queue, latency stays low, and the frame rate automatically matches how fast the server can process. If no result arrives within 5 s, one extra frame is allowed, but never more.

Where: web/js/frames.js, web/js/connection.js

Concurrency

  • The async event loop must never block, so decoding and inference run in a worker thread (asyncio.to_thread).
  • One TensorFlow model can be shared by several tabs, so a lock serialises predictions. Each tab still has its own engine (smoothing history and text).
  • Each model is loaded once and warmed up with dummy predictions, because the first prediction takes 1–5 s. The default model is preloaded in the background when the server starts.
  • Fine-tuning runs in a separate subprocess, so heavy training can't freeze or crash the server. Its output is streamed to the Personalise tab.

Coordinates and mirroring

The server always works on the unmirrored frame and returns coordinates normalised to 0–1, so they don't depend on resolution. The video is displayed mirrored, like a selfie camera, so the browser draws each point at x′ = 1 − x. A canvas over the video draws the landmarks and the crop box: green when the prediction is confident, amber when it is uncertain.

Text-to-speech

  • Web app: the browser's Web Speech API (speechSynthesis), which uses the operating system's voices and works offline.
  • Autoplay policy: Chrome and Edge refuse speech (error not-allowed) until the user has clicked or pressed a key on the page. The app detects this, shows a "Speech is waiting for a click" banner, and unlocks speech on the first click with a silent utterance. It also detects when no voices are installed.
  • webcam.py: Windows SAPI through COM (pywin32), and pyttsx3 on macOS/Linux. Speech runs on a background thread fed by a queue (producer–consumer), so the video never freezes while it speaks.

G. Security and privacy

Local only

The server listens only on 127.0.0.1, so other computers can't reach it. Camera frames go from the browser to this local server and nowhere else. There are no cloud APIs, and speech is offline.

Host and Origin checks

Any website open in the same browser could try to talk to localhost. Two checks stop this:

  • Host header allowlist: this blocks DNS rebinding, an attack in which a malicious domain is re-pointed to 127.0.0.1 so the browser treats it as the same site.
  • Origin check on every HTTP request and on the WebSocket: this blocks cross-site WebSocket hijacking. Browsers do not apply the same-origin policy to WebSockets, so the server has to check the Origin itself. Rejected WebSockets are closed with code 1008 (policy violation).

Input hardening

  • Clients choose models by id, never by file path, which rules out path traversal.
  • Frames over 3 MB are rejected.
  • Settings are type-checked, NaN is rejected, and every value is clamped to safe limits.
  • The automatic API documentation pages are disabled, and responses are sent with Cache-Control: no-store.

H. Software engineering

Modular design with one shared engine

The code is a package (signspeak/) with one responsibility per module: hands, model, composer, engine, speech, server, registry, userdata, practice, dataset, camera. The web app and the OpenCV version share one RecognitionEngine, so the pipeline is implemented only once. Components such as the model cache and hand tracker are passed in (dependency injection), so tests can substitute fakes.

Testing

70 unit tests (python -m unittest discover -s tests -t .), none of which need a camera or the model. They cover:

  • crop geometry: always inside the frame, always contains both hands, never empty, checked with random boxes;
  • every typing rule;
  • dataset listing;
  • the fine-tuning mask and bundle fingerprint;
  • the web flows and the security checks;
  • the on-screen layout at several frame sizes.

Reproducibility and robustness

  • Pinned dependency versions (TensorFlow 2.17.1, Keras 3.15.1, MediaPipe 0.10.21, …), fixed random seeds (42), and deterministic, evenly spaced sampling.
  • Training and fine-tuning never overwrite models/. Each run is saved to runs/<name>/ with a metrics.json.
  • Webcam opening on Windows: try Media Foundation first and fall back to DirectShow, wait for a real first frame, and tolerate camera dropouts of up to 3 s.

The test figures use the same 4 signers the model was trained on, so expect lower accuracy for a new person, new lighting or a new camera. The personalised held-out take was recorded in the same session, so accuracy on another day will be somewhat lower.

Limitations and future scope

Limitations

  • J and Z involve motion, but the model classifies single frames, so it sees only a static pose.
  • Small signer pool (4 people): accuracy drops for other people, skin tones, backgrounds and lighting. Personalisation reduces this.
  • Letters only: no digits, no word-level signs, no grammar.
  • Fingerspelling is slow compared with a full conversation.
  • Works best with even lighting, a plain top, and both hands at chest height.

Future scope

  • Sequence models (LSTM/GRU, temporal CNN or Transformer) on landmark sequences, for J, Z and word-level signs.
  • Landmark-based classifier, or a hybrid of image and landmarks, which is more robust to background, lighting and skin tone.
  • A larger, more diverse dataset: more signers, rooms and cameras.
  • Word suggestions / spell correction from a dictionary or language model.
  • On-device deployment: TensorFlow Lite on phones, or TensorFlow.js fully in the browser.
  • Two-way communication: speech-to-text-to-sign animation.

The project

Explain your project in one or two sentences.

SignSpeak recognises Indian Sign Language fingerspelling from a webcam in real time. MediaPipe finds the hands, a fine-tuned MobileNetV2 classifies the crop into A–Z, a hold-to-confirm composer turns letters into words, and the words are spoken, all offline on a laptop CPU.

Why Indian Sign Language, and why is it harder than ASL?

Most tools and datasets target American Sign Language. In the ISL alphabet most letters use both hands, while ASL letters use one. The crop must therefore contain both hands together, and ASL models and one-hand pipelines can't be reused.

Why fingerspelling and not full signs?

Fingerspelling is a closed set of 26 handshapes, mostly static. That suits single-frame image classification and a dataset of about 26k photos. It also covers names and words that have no sign. Word-level signs involve motion and need sequence models and much larger video datasets, which we list as future work.

What was your own contribution compared to the starting code?

The prototype had the trained model but a broken pipeline. We:

  • fixed the crop for two-handed ISL letters (calibrated margins, stretch, no drawn landmarks);
  • added flip averaging, the hold-to-confirm composer and speech;
  • built the web app, the personalisation system (masked fine-tuning with replay and bundled features) and the evaluation and training scripts;
  • wrote 70 tests.

See What we improved.

Model and training

Why MobileNetV2 and not ResNet or VGG?

It is designed for mobile and CPU use: about 2.3 M parameters (22 MB) against about 25.6 M for ResNet-50 and about 138 M for VGG-16. It runs in real time on a laptop without a GPU, has ImageNet weights available in Keras, and gives a good accuracy/speed trade-off.

What is transfer learning and why did you use it?

Transfer learning reuses features a network learned on a large dataset (ImageNet) for a new task, training only a new head and then lightly fine-tuning the top layers. It needs far less data and compute. 26k images from 4 signers would overfit a deep CNN trained from scratch.

What is a depthwise separable convolution?

A standard convolution split into two steps: a 3×3 filter applied to each channel separately (depthwise), then a 1×1 convolution that mixes the channels (pointwise). The cost falls by a factor of about 1/N + 1/k², roughly 8–9× fewer operations for 3×3 kernels, with similar accuracy.

What is an inverted residual block?

The input is narrow. A 1×1 conv expands it (×6), a 3×3 depthwise conv filters it, and a linear 1×1 conv projects it back to narrow. A skip connection joins the narrow input and output. It is "inverted" because a classic ResNet bottleneck is wide → narrow → wide. The final projection has no ReLU (a "linear bottleneck"), because ReLU in a low-dimensional space throws information away.

Why global average pooling instead of Flatten?

GAP averages each of the 1280 7×7 feature maps into one value. The dense layer then needs only 1280×26+26 = 33,306 parameters, against about 1.63 M after Flatten. Fewer parameters mean less overfitting, and averaging adds some tolerance to where the hand sits in the image.

Why softmax with categorical cross-entropy?

The letters are mutually exclusive. Softmax turns 26 raw scores into probabilities that sum to 1. Cross-entropy (−log of the true class's probability) heavily penalises confident mistakes, and it is the maximum-likelihood loss for multi-class classification.

What does dropout do? Is it used during prediction?

During training it randomly zeroes 20% of the 1280 features, so the network can't depend on any single feature; this acts as regularisation. At prediction time it is switched off.

Why train in two stages?

A newly initialised head produces large, noisy gradients that would damage the pretrained backbone. So the head is trained first with the backbone frozen (learning rate 1e-3). Then the top blocks (from block_14) are unfrozen and fine-tuned at a much smaller rate (1e-5), adapting high-level features without destroying them.

Why keep BatchNorm frozen while fine-tuning?

BatchNorm layers store running means and variances learned on ImageNet. Updating them from small batches of new data shifts those statistics and can wreck accuracy. We call the backbone with training=False and never unfreeze BatchNorm layers, which is the standard Keras recommendation for fine-tuning.

How did you prevent overfitting?

Transfer learning (few new parameters); data augmentation (rotation ±18°, zoom, translation, contrast); dropout 0.2; early stopping on validation accuracy (patience 3, best weights restored); and keeping the test split untouched until the end.

What preprocessing does the input go through?

BGR → RGB, a stretch-resize to 224×224 (bilinear), then a float32 array of 0–255 values. The scaling to [−1, 1] (x/127.5 − 1) happens inside the model, so it is done in exactly one place and can't be applied twice.

What are epochs, batch size and learning rate here?

An epoch is one pass over the training set. The batch size is the number of images per gradient step (32 when training, 64 when fine-tuning on features). The learning rate is the step size: 1e-3 for the head, 1e-5 for backbone fine-tuning, 1e-3 for personal fine-tuning. The optimiser is Adam.

Vision pipeline

How do you detect the hands?

With MediaPipe Hands, a two-stage model. A palm detector locates hands, then a landmark model predicts 21 3-D keypoints per hand. In video mode it tracks hands from the previous frame and re-runs detection only when tracking is lost. We take the bounding box of each hand's landmarks.

Why classify an image crop instead of the landmark coordinates?

It is a design trade-off. The dataset and the pretrained model were image-based, and the image keeps information such as overlapping or occluded fingers in two-handed letters, where landmark detection is least reliable. A landmark classifier would be faster and less sensitive to background and lighting, so we list it, or a hybrid, as future work.

How do you handle two hands, or someone else's hand in the frame?

We take the largest hand and include another hand only if the gap between their boxes is at most the larger hand's longer side. Two-handed letters touch or overlap, so they stay together, while a distant hand is ignored. The boxes are joined into one, and then the margins are added.

Why is the crop stretched instead of kept square?

The training images are non-square crops stretched to 224×224, so the model learned stretched hands. Reproducing that framing gave 84.5–85.5% in the simulated-webcam test, against 80.6% for an aspect-preserving square crop. The inference input must match the training input.

How did you choose the crop margins?

By measurement. On the Validation split, we compared MediaPipe's hand box with each dataset image's borders. The median margins were left 0.42, top 0.27, right 0.24 and bottom 0.31. We made them symmetric (0.33 left/right, 0.29 top/bottom) so left- and right-handed signers are treated alike. Every margin from 0.25 to 0.40 performed about the same.

What is flip averaging and does it help?

It is test-time augmentation: the crop and its mirror image are both classified and the probabilities averaged. The dataset mixes mirrored and unmirrored photos, so this makes left/right-handed signers and mirrored cameras equally reliable. Test accuracy goes from 90.7% to 91.3%, for about 1.3× the compute.

Real-time logic

How do you stop flickering predictions from being typed?

Three layers of protection:

  1. a moving average of probabilities over 7 frames;
  2. a 0.60 confidence threshold;
  3. hold-to-confirm, where the same confident letter must last 1 s and at least 3 frames.

A brief mistake while the hands move between signs never gets typed.

How can a user type double letters, like the LL in HELLO?

After a letter is typed, the composer waits for a release: no hand, an uncertain prediction, or a different letter, for at least 0.3 s. Signing the same letter again after that types it again.

How are words separated and spoken?

Lowering your hands for 2 s after a letter types one space (once per word). The server then reports the finished word, and the browser speaks it. The Space key or button does the same.

How do you keep it real-time? What about latency?

Several measures work together:

  • Small model: MobileNetV2 is light enough to run quickly on a CPU.
  • Fast tracking: MediaPipe tracks hands between frames instead of detecting them from scratch every time.
  • One frame in flight: the browser waits for each result before sending the next frame, so a queue never builds up and the frame rate adapts to the computer's speed.
  • Warm-up: models are warmed up when loaded, so the first frame isn't slow.
  • Smooth video: the browser plays the video at full frame rate locally, and only recognition runs at the server's pace.
What is the composer, conceptually?

A small finite-state machine (armed → holding → typed/waiting for release → armed). It debounces a noisy signal, just as a keyboard debounces a physical key. It is pure logic, so 22 unit tests cover its rules.

Personalisation

Why did you need personalisation?

Domain shift. The model learned from 4 signers, and a new user's hands, camera, room and way of forming letters differ. On our user's held-out take the original model scored only 57.6%; letters such as D were consistently read as P.

How can you fine-tune without a GPU in about a minute?

Only the final Dense layer (33k parameters) is trained. The backbone is frozen, so each image's 1280-number feature vector is computed once and cached. Training then runs on short vectors instead of images, which is fast on a CPU.

What is catastrophic forgetting and how did you avoid it?

A network fine-tuned only on new data forgets its old knowledge. We used two defences:

  • Replay: 100 original training images per letter are mixed into fine-tuning.
  • Weight mask: only the recorded letters' weights can change.

On a check set of 780 dataset images, accuracy went from 91.5% to 91.7%, so the model didn't forget.

Why mask the weights of unrecorded letters?

When the whole final layer was retrained, letter I dropped from 100% to 73% on the dataset even though it was never recorded. With W = W₀ + ΔW ⊙ mask, unrecorded letters keep exactly their original weights, so they can't drift.

Why must the user record all letters, not just the wrong ones?

Shortcut learning. When only six letters were recorded, every image from the user's camera belonged to those six, so the model learned "this camera means one of these six", and F, H and R broke. Recording all 26 makes the camera useless as a clue, so the model must rely on hand shape. The result was 57.6% → 98.6%.

Why split training/validation by take and not by frame?

Frames within a take are near-duplicates. A random frame split would leak almost identical images into validation and inflate the score (data leakage). We hold out the entire last take of each letter.

How does fine-tuning work without downloading the 657 MB dataset?

Only the features of the replay and test images are needed, and they ship as a 15 MB float16 file. A SHA-256 fingerprint of all layers before the last one guarantees the features match the model's feature extractor; a mismatched bundle is refused.

Evaluation

What accuracy did you achieve?
  • 90.6% on the 5,198 RealSign test images as stored.
  • 84.8% through the simulated webcam pipeline.
  • For our user, the personalised model reached 98.6% on a held-out take, up from 57.6%.
Why is live/webcam accuracy lower than test accuracy?

Live use adds hand-detection and crop errors, and differences in camera, lighting, background and signer (domain shift). The test set comes from the same 4 signers as training. That is why we also report the simulated-webcam figure and built personalisation.

Is accuracy a good metric here? What about precision and recall?

The classes are balanced (200 test images per letter), so accuracy isn't distorted by a majority class. We also report per-letter accuracy (equal to per-class recall) and the confusion matrix, from which precision, recall and F1 can be computed for each letter.

What is the difference between the validation and test sets?

Validation guides decisions during development, such as early stopping and choosing the crop margins. The test set is used only once, at the end, so it gives an unbiased estimate of performance.

Which letters are weakest and why?

Z (27%), S (51%), V (61%), W (66%), Q (72%), N and X (75%). Their handshapes are close to other letters, differing by one finger (V→U, S→I, N→H, Q→R). Z also involves motion, which a single frame can't capture.

What is a confusion matrix?

A 26×26 table with one row per true letter and one column per predicted letter. The diagonal holds correct predictions, and everything off the diagonal shows which letters get mistaken for which. evaluate.py --confusion-csv exports it.

Web, systems and security

Why a web app instead of only an OpenCV window?

It allows a much richer interface (tabs, settings, overlays, history, practice and personalisation), runs on any OS with a browser, and lets the browser handle the camera and speech. Python stays responsible for vision and ML. The OpenCV version, webcam.py, still works and uses the same engine.

Why WebSockets instead of normal HTTP requests?

A WebSocket is one persistent, two-way connection. There is no new request or header overhead for every frame, binary JPEG data can be sent directly, and the server can push results and status messages back at any time.

What are FastAPI, Uvicorn and ASGI?

FastAPI is a Python web framework that defines our HTTP routes and the WebSocket endpoint. Uvicorn is the server process that runs it. ASGI is the asynchronous interface between them, which supports WebSockets and async code.

How does the server stay responsive while running TensorFlow?
  • Inference runs in worker threads (asyncio.to_thread), so the event loop isn't blocked.
  • A lock serialises calls to a model shared by several tabs.
  • Models are cached and warmed up, and the default model is preloaded at start-up.
  • Fine-tuning runs as a separate subprocess.
Is the user's video sent to the internet? Is it private?

No. The server binds only to 127.0.0.1, frames travel only from the browser to that local server, and there are no cloud services. Recordings stay in data/user/ on the computer and are excluded from git.

What security issues did you consider?

Any website open in the same browser could try to reach localhost. We block this in three ways:

  • a Host header allowlist (defeats DNS rebinding);
  • an Origin check on HTTP requests and the WebSocket (defeats cross-site WebSocket hijacking);
  • input hardening: model ids instead of file paths (no path traversal), a 3 MB frame limit, validated and clamped settings, and disabled API documentation pages.
Why does browser speech sometimes stay silent?

Chrome and Edge block speechSynthesis until the user has clicked or typed on the page (error not-allowed). The app detects this, shows a banner asking for one click, and unlocks speech on the first interaction. It also detects when the OS has no voices installed.

Limitations and future work

How would you recognise J and Z, or whole words?

With a sequence model that sees time: an LSTM/GRU, a temporal CNN or a Transformer over sequences of MediaPipe landmarks (or image features) from several frames. That would need a video dataset of the moving letters and signs.

How would you make it work better for everyone without personalisation?

Train on many more signers, skin tones, rooms and cameras; use stronger augmentation; and consider landmark-based or hybrid inputs, which ignore background and lighting.

Could this run on a phone?

Yes. MobileNetV2 was designed for mobile, and the model could be converted to TensorFlow Lite. MediaPipe also runs on Android, iOS and the web, and TensorFlow.js could run the whole system inside the browser.

Glossary

One-line definitions to have ready.

Epoch
One full pass over the training data.
Batch size
Number of examples used for one gradient update.
Learning rate
Size of each weight-update step.
Adam
Optimiser with momentum and adaptive per-parameter learning rates.
Logits
Raw class scores before softmax.
Softmax
Turns scores into probabilities that sum to 1.
Cross-entropy
Loss = −log(probability given to the correct class).
Overfitting
Memorising training data; good on train, poor on new data.
Regularisation
Anything that discourages overfitting (dropout, augmentation, early stopping).
Data augmentation
Random changes to training images to add variety.
Transfer learning
Reusing a model trained on one task as the starting point for another.
Fine-tuning
Continuing to train some pretrained layers at a low learning rate.
Feature vector / embedding
The 1280 numbers summarising an image, just before the final layer.
Inference
Using a trained model to make predictions.
Landmark
A keypoint on the hand; MediaPipe gives 21 per hand.
Domain shift
Difference between training data and real-use data.
Data leakage
Test/validation data (or near-copies) seen in training, inflating scores.
Catastrophic forgetting
Losing old knowledge when trained only on new data.
Shortcut learning
Model uses a spurious clue (e.g. the camera) instead of the real signal.
Test-time augmentation
Averaging predictions over transformed copies of an input (here: mirror).
Confusion matrix
True class × predicted class count table.
Backpressure
A sender slowing down to match how fast the receiver can process.
Debouncing
Accepting a signal only after it has been stable for a while.
WebSocket
Persistent two-way connection between browser and server.
ASGI
Asynchronous Python web-server interface (supports WebSockets).
DNS rebinding
Attack that points a malicious domain at 127.0.0.1 to reach local servers.
